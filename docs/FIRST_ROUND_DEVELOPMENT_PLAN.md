# Latent CoT 编辑：第一轮开发计划

本地开发、远程服务器验证与实验、结果回传及本地分析，统一遵循 [本地开发与远程实验规范](LOCAL_REMOTE_WORKFLOW.md)。

## 1. 研究问题与本轮目标

我们希望研究：当模型自然回答错误时，能否确定 latent 推理是否参与了错误形成，找到候选问题位置，并通过局部修改，让模型继续推理后得到正确答案。

错误可能出现在推理的开头、中间或结尾，不预设它一定是某个中间数值算错，也不预设一个错误只能对应一个 latent 步骤。

**第一轮的交付目标是一个可信的干预实验平台：原始评测、原样恢复验证、逐位置干预。** 本轮不要求完成自动错误定位或语义修复算法；平台跑通后，再基于实际错误案例设计修复方法。

必须区分三个结论层次：

- 干预某位置后答案变化：说明该位置对输出有影响。
- 某位置的干预使错误答案变正确：说明该位置存在有效的干预机会。
- 识别该位置的错误内容，并进行有针对性的修复：才进一步支持“定位并修复了推理错误”。

前两项不能直接替代第三项。有效修复位置也不必等于错误最初发生的位置。

## 2. 开发基础

### 2.1 主仓库与首个模型

以原论文官方仓库 [J1mL1/causal-latent-cot](https://github.com/J1mL1/causal-latent-cot) 为开发基础，第一阶段只接入 Coconut。

该仓库已有步骤干预、充分性分析和模型封装。其 [CoconutWrapper](https://github.com/J1mL1/causal-latent-cot/blob/main/common/models/coconut_model.py) 提供以下接口：

```python
h_t, state = model.forward_until_step(inputs, step=t)

# 原样恢复验证时，直接使用 h_t；干预时替换为修改后的向量。
h_t_modified = intervention(h_t)

result = model.rollout_from_step(
    h_t_modified,
    state,
    continue_latents=True,
)
```

`intervention` 是我们新增的逻辑，其他调用为已有接口。指定步骤的反馈向量在送入下一步之前被返回；修改后继续计算剩余 latent 步骤，再生成答案。

### 2.2 其他仓库的用途

| 仓库 | 本项目中的用途 |
| --- | --- |
| [facebookresearch/coconut](https://github.com/facebookresearch/coconut) | 提供底层模型与训练实现，满足主仓库 wrapper 的依赖 |
| [are-lrms-easily-interpretable](https://github.com/connordilgren/are-lrms-easily-interpretable) | 参考 checkpoint 加载、数据处理、评测配置和辅助分析 |
| [zhenyi4/codi](https://github.com/zhenyi4/codi) | 后续作为第二种 latent reasoning 方法，本轮暂不接入 |

先使用已训练的 GPT-2 + Coconut，减少从训练开始的成本。GSM8K 可参考公开的 [gpt2-gsm8k-coconut checkpoint](https://huggingface.co/connordilgren/gpt2-gsm8k-coconut)；ProsQA 权重从对应仓库的 [预训练模型说明](https://github.com/connordilgren/are-lrms-easily-interpretable#pretrained-models) 中选择并核对。

GSM8K checkpoint 的训练数据是 GSM8K-Aug，评测可使用原始 GSM8K test。该权重是原始 PyTorch state dict，需要构建相匹配的基础模型、特殊 token 和 wrapper 后加载，不能直接假设支持 `from_pretrained`。

## 3. 当前数据与适配

当前项目已下载：

```text
data/
├── gsm8k/
│   ├── train.jsonl
│   └── test.jsonl
└── prosqa/
    ├── train.json
    ├── valid.json
    └── test.json
```

- **GSM8K：** 观察自然发生的算术推理失败及干预效果。
- **ProsQA：** 用结构明确的推理任务辅助分析位置和传播，但先验证选定 checkpoint 是否实际依赖 latent 计算。

新增统一的数据适配层，输出 `sample_id`、`question`、`gold_answer`，以及可选的参考 `steps`。保留原始文件，转换结果另存。

GSM8K 需要从原始 `answer` 字段提取最终答案；ProsQA 使用其答案字段。模型输入只包含问题及模型要求的格式 token，参考答案和参考步骤单独用于评估。参考文本步骤不直接作为 latent 步骤的错误标签。

本轮使用现成 checkpoint 做推理实验，不启动训练。未来若自行训练，再处理训练轨迹和 GSM8K-Aug 的适配。

## 4. 实施步骤与验收标准

### 阶段 A：固定环境，跑通原始评测

实施内容：

1. 获取主仓库及 Coconut 依赖，记录各自的 commit。
2. 固定 Python、PyTorch、Transformers 等实际使用的版本。
3. 接入一个 GPT-2 + Coconut checkpoint，核对权重加载结果、特殊 token 顺序、输入格式、latent 步数和生成参数。
4. 分别适配 GSM8K 和 ProsQA，先用少量固定样本检查，再运行基线评测。
5. 记录完整生成文本、提取答案、正确性及解析失败原因，建立自然正确与自然错误样本集合。

验收标准：

- 相同模型、样本与配置下，重复推理结果可复现。
- 答案解析失败单独报告，不混同于推理错误。
- 权重缺失或多余的参数有明确解释，不仅以“加载未报错”为成功依据。
- 报告实际准确率与自然错误数量；不预先假定两个数据集都有足够的可研究错误。

输出：基线结果、错误样本列表、环境与模型配置记录。

### 阶段 B：验证原样恢复与轨迹记录

对同一个问题、每个可用 latent 步骤，执行：

```text
原始完整推理
    ↕ 比较
运行到步骤 t → 保留 h_t 原值 → 继续剩余推理
```

实施内容：

1. 为自然推理和干预推理增加统一的轨迹记录。
2. 记录反馈向量、步骤编号、向量范数、必要的 logits，以及恢复推理所需的状态。
3. 使用 eval 模式、固定生成参数和 greedy decoding，逐位置进行原样恢复验证。
4. 比较恢复后的 latent 轨迹、答案 logits 和最终生成结果。
5. 检查同一前缀状态是否能被独立复用，避免不同干预分支相互污染。

验收标准：

- 所有可用 latent 位置都能暂停并继续，包括第一步和最后一步。
- 原样恢复后的轨迹与 logits 在按 dtype 设定的数值容差内一致，最终生成结果一致。
- 如出现不一致，记录最大误差和首次分歧位置，并修复后再开展效果实验。
- 数据不同时长、不同问题长度时，位置索引、attention mask 和缓存处理正确。

输出：原样恢复验证报告、轨迹文件及可重复运行的验证入口。

### 阶段 C：逐位置干预，建立对照

在保持问题、模型权重、latent 步数和解码参数一致的条件下，分别干预每个 latent 步骤，然后重新计算后续推理。

本轮先实现三种操作：

| 操作 | 用途 |
| --- | --- |
| 原样传回 | 检查实验路径本身是否改变结果 |
| 置零 | 复现简单消融，测量该位置的影响 |
| 不同强度的随机扰动 | 建立非定向修改的对照，观察输出对扰动的敏感性 |

置零和随机扰动属于诊断操作，不称为语义修复。随机扰动需要记录随机种子，并按原向量范数定义强度，避免不同位置的尺度差异影响比较。

同时在自然错误样本和自然正确样本上运行，记录：

- 错误 → 正确、正确 → 错误，以及答案变化但正确性不变的情况。
- 各位置、各操作、各强度的变化率及对应样本数。
- 修改后后续轨迹的变化，包括首次明显分歧的位置。
- 若条件允许，补充不同 latent 步数的对照，辅助检查模型是否利用 latent rollout。

验收标准：

- 每个结果可追溯到样本、模型、位置、操作、强度和随机种子。
- 干预后继续计算后续 latent，不沿用原始轨迹的后续向量。
- 正向与负向变化分别报告，不只报告净准确率。
- 原样对照通过；置零与随机扰动均能完整运行并产出结果。
- 保留具有代表性的案例，支持人工比较干预前后变化。

输出：逐位置干预结果表、位置效果图和案例记录。

## 5. 建议新增的代码模块

以下是职责划分，实际路径在获取主仓库后按其结构调整：

| 模块 | 职责 |
| --- | --- |
| `data_adapter` | 读取两个数据集、分配稳定样本 ID、规范化答案 |
| `baseline_eval` | 运行自然推理、计算正确性、导出错误集合 |
| `trace_recorder` | 记录 latent 轨迹和运行元信息 |
| `resume_check` | 逐位置执行原样恢复验证 |
| `interventions` | 提供 identity、zero、random 操作 |
| `step_sweep` | 遍历位置和干预参数，恢复并继续推理 |
| `analysis` | 汇总转移率、轨迹差异和具体案例 |

每条实验记录至少包含：`sample_id`、数据集及 split、模型与 checkpoint 标识、输入格式、latent 步数、干预位置、操作及参数、随机种子、基线与干预后的答案、两次正确性、轨迹文件位置。

轻量结果存为 JSONL；向量等较大张量单独保存，避免写入 JSONL。运行配置和代码版本随结果保留。

## 6. 实现边界与待核对事项

1. **反馈向量不是全部推理状态。** 当前首选接口修改的是下一步输入的 latent 向量，历史信息也保存在 KV cache 中。本轮结果只覆盖这一干预位置，修复失败不能直接排除其他状态中的问题。
2. **步骤边界要明确。** 当前 wrapper 的 latent 步骤使用从 1 开始的索引。第一步和最后一步都应检查，但 prompt 内部计算和答案生成阶段的内部节点不自动包含在这个范围内。
3. **梯度路径需要另行核对。** 当前代码提取 latent 向量时存在 `.detach()`。本轮前向干预可以先开展；后续若通过梯度优化编辑量，需要检查完整传播路径，不能只依赖 `allow_grad=True`。
4. **外部 checkpoint 需要适配验证。** 权重、特殊 token、prompt 格式和 latent 步数要与训练配置相匹配；主仓库和 checkpoint 来源不同，不能默认直接兼容。

现已使用随机初始化的微型 GPT-2 验证恢复与干预逻辑；真实 checkpoint 的加载、准确率和干预效果仍需在服务器验证。

## 7. 第一轮结束后的决策

完成本轮后，依据实际结果回答：

1. 哪个模型与数据集组合同时具有可复现的自然错误和明显的 latent 干预效应？
2. 哪些位置或区域值得进一步研究？效应是否稳定，是否也会破坏正确样本？
3. 哪些案例可以提出具体、可检验的错误内容假设？

随后选择少量案例开发有依据的局部修复，并与随机扰动、其他位置的相同修改进行比较。若使用正确答案或参考轨迹来构造修复，明确标注为 oracle 诊断，不将其直接解释为自动修复能力。

本轮不预设一定能找到单一错误节点，也不把消融造成的答案变化等同于定位成功。后续算法选择应由这些实验结果决定。
